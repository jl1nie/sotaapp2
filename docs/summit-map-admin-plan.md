# 山頂の簡易地図と POTA の判定を、管理画面で管理する計画

作成: 2026-10-25 / 状態: 計画(未着手)

## 1. 目的

- 山頂ごとの「どの市区町村(JCC/JCG)を選ぶと、どの POTA に当たるか」の**目視の答え**を、本番の DB に直接持つ。
- 手元のバッチは**推定**(空間計算の結果)と**地図の下地**だけを入れる。目視の答えは、バッチを何度流し直しても消えない・上書きされない。
- 見直しは、claude.ai の判定表ではなく、sotaapp2 の管理画面で行う。

### 今の問題

- `POST /sota/import/pota` は `summit_pota` を全部消してから入れ直す(`replace_summit_pota`)。目視の行も、バッチの CSV に入っていなければ消える。
- 目視の答えの正本が、手元のファイル(判定表の書き出し `db_dump5/verdicts`、`CONFIRMED` の一覧、`manual_fixes.csv`)に散らばっている。
- 目視で「なし」と決めた組は、`summit_pota` に行がない(CSV は all / part だけを出す)。DB を見ても、「なし」と目視したのか、まだ見ていないのか区別できない。
- 地図の GeoJSON(`summit_maps`)の muni フィーチャに、答え(`pota: [{code, name, coverage}]`)が焼き込まれている。答えを直すには、地図も作り直してアップロードし直す必要がある。

## 2. 守ること

旧判定表の事故(2026-10-24。確定するとカードがせり上がり、見ていない山頂が既定の答えのまま「目視済み」で本番に入った)を踏まえる。

1. **答えを事前に選ばない。** 推定の答えは参考として並べて表示するが、ラジオボタンの初期値にはしない。
2. **すべての組を選ぶまで「確定」を押せない。**
3. **確定しても画面は動かない。** カードのせり上がりや、次の山頂への自動の移動はしない。次へ進むのは、明示的な「次の山頂」ボタンだけ。
4. **サーバーが保存を返してから「確定」と表示する。** 失敗したら、画面の状態を戻して知らせる。
5. **推定と目視を、表も表示も分ける。** 「保存されている」を「確認済み」と言い換えない。
6. **前提が変わった目視は「要再確認」にする。** 山頂の位置・公園区域・市区町村が変わったら、その山頂の目視は古い前提の答えになる。黙って使い続けず、一覧に出す(10 章)。

## 3. データの設計

### 3.1 表

| 表 | 書く人 | 中身 |
|---|---|---|
| `summit_pota_estimates` | バッチ(取り込み) | 候補の組すべて(**なしも含む**)と推定の答え・根拠の数値 |
| `summit_estimates_meta` | バッチ(取り込み) | 山頂ごとの推定の入力(位置・データの版・入力の指紋 `input_rev`) |
| `summit_pota_verdicts` | 管理画面 | 目視の答え(all / part / none)。取り込みでは触らない |
| `summit_reviews` | 管理画面 | 山頂ごとの確定の記録(誰が・いつ・どの候補の版に対して) |
| `summit_pota_log` | 管理画面 | 答えの変更の履歴(前の答え → 後の答え) |
| `summit_maps` | バッチ + サーバー | 下地の GeoJSON と、答えを差し込んだ配信用の GeoJSON |

```sql
CREATE TABLE summit_pota_estimates (
    summit_code VARCHAR(255) NOT NULL,
    muni_key    VARCHAR(255) NOT NULL,   -- JCC#1115 / JCG#11001B
    muni_name   VARCHAR(255) NOT NULL,
    pota_code   VARCHAR(255) NOT NULL,
    coverage    VARCHAR(16)  NOT NULL,   -- all / part / none(推定)
    pct         REAL,                    -- ゾーンのうち公園に入る割合
    px          INTEGER,                 -- 当たった画素の数
    noise       INTEGER NOT NULL DEFAULT 0,
    note        TEXT,                    -- 補正の規則が働いた理由など
    PRIMARY KEY (summit_code, muni_key, pota_code)
);

CREATE TABLE summit_pota_verdicts (
    summit_code VARCHAR(255) NOT NULL,
    muni_key    VARCHAR(255) NOT NULL,
    pota_code   VARCHAR(255) NOT NULL,
    coverage    VARCHAR(16)  NOT NULL,   -- all / part / none(目視)
    PRIMARY KEY (summit_code, muni_key, pota_code)
);

CREATE TABLE summit_reviews (
    summit_code    VARCHAR(255) NOT NULL PRIMARY KEY,
    input_rev      VARCHAR(64)  NOT NULL, -- 確定したときの推定の入力の指紋(10.1)
    reviewed_by    VARCHAR(255) NOT NULL, -- Firebase の UID
    reviewed_at    INTEGER      NOT NULL,
    note           TEXT
);

-- 推定を計算したときの入力。山頂ごとに 1 行。バッチが入れる
CREATE TABLE summit_estimates_meta (
    summit_code  VARCHAR(255) NOT NULL PRIMARY KEY,
    input_rev    VARCHAR(64)  NOT NULL, -- 入力の指紋(10.1)
    latitude     REAL NOT NULL,         -- 計算に使った山頂の位置
    longitude    REAL NOT NULL,
    data_version VARCHAR(255) NOT NULL, -- 公園区域・市区町村境・munitable の版(例 jaffpota-v24/N03-2024/munitable-2026-10)
    computed_at  INTEGER NOT NULL
);

CREATE TABLE summit_pota_log (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    summit_code VARCHAR(255) NOT NULL,
    muni_key    VARCHAR(255) NOT NULL,
    pota_code   VARCHAR(255) NOT NULL,
    before      VARCHAR(16),             -- NULL: 目視なし(推定のまま)だった
    after       VARCHAR(16),             -- NULL: 目視を取り消した
    changed_by  VARCHAR(255) NOT NULL,
    changed_at  INTEGER      NOT NULL
);
```

### 3.2 配信する答え

組ごとに「目視があれば目視、なければ推定」を使う。`verified` は目視があるときだけ 1 にする。

- `GET /sota/summits/{code}/pota` の形は今と同じ(all / part の組だけを返す)。FLEonline 側の変更は要らない。
- 今の `summit_pota` は、この規則で引く VIEW に置き換える(または repository の SELECT を書き換える)。

### 3.3 山頂の状態

一覧の絞り込みに使う。表に持たず、引くときに計算する。

| 状態 | 条件 |
|---|---|
| 未確認 | `summit_reviews` に行がない |
| 確定 | 行があり、`input_rev` が今の推定の `input_rev` と同じ |
| 要再確認 | 行があるが、`input_rev` が違う(山頂の位置・公園区域・市区町村が変わった) |
| 地図なし | `sota_references` にあるが、推定・地図がない(新しい山頂など) |
| 推定が古い | 山頂の今の位置が、推定に使った位置から 20 m 以上ずれている |
| 要確認(推定) | 未確認のうち、推定に「一部」「境界付近」「補正の規則が働いた」組がある |

### 3.4 地図

- バッチは**下地**を入れる。下地では、muni フィーチャに候補の組の一覧だけを持たせ、答えは持たせない。また、候補の組のうち公園と重なる部分があるものは、答えにかかわらず、公園の区域(park フィーチャ)をすべて入れる(今は「一部」の組だけ)。
- 下地には、判定にだけ使う層も入れる: 地図の範囲にかかる公園の区域の元の形(市区町村で切らないもの)と、最高点(DEM のいちばん高い点)。旧判定表の「判定用の地図」と同じものを描くため。kind は `judge_park` / `peak` とし、配信用からは外す(端末に送る量を増やさない)。
- サーバーは、下地に今の答えを差し込んだ配信用の GeoJSON を作って保存する。差し込むのは muni の `pota` と、「一部」でない park フィーチャを外す処理。
  - 作り直すのは、**書いたとき**(地図の取り込み・目視の確定・推定の取り込み)だけにする。配信のたびに組み立て直さない(本番の CPU の割り当てが小さいので)。
  - 推定の取り込みでは、全山頂の作り直しになる。500 件ずつに分けて、ほかの要求を止めない。
- 配信の API(`/summits/{code}/map`、`/sota/maps?prefix=`)の形は今と同じ。

## 4. API

保護(`with_auth`)の下に置く。

| メソッド | パス | 中身 |
|---|---|---|
| POST | `/sota/import/pota` | 推定の CSV で `summit_pota_estimates` を置き換える。**目視の表には触らない**。結果に「要再確認になった山頂の数」を返す |
| POST | `/sota/import/maps` | 下地の JSONL を upsert し、配信用を作り直す |
| GET | `/sota/review/summits?prefix=&status=&q=` | 山頂の一覧(状態・推定の要約・確定した人と日時) |
| GET | `/sota/review/summits/{code}` | 候補の組・推定・目視・`input_rev`・下地の地図・履歴 |
| PUT | `/sota/review/summits/{code}` | 全組の答えを一度に確定する(下記) |
| DELETE | `/sota/review/summits/{code}` | 目視を取り消して推定に戻す(履歴は残す) |

PUT の決まり:

- 本文は `{ input_rev, answers: [{muni_key, pota_code, coverage}] }`。
- 今の候補の組と、答えの組が**ぴったり一致**しないと 400(足りない・余計な組がある)。
- `input_rev` が今の推定と違えば 409(見ている間にバッチが流れた)。画面は読み直しを促す。
- 1 つのトランザクションで、verdicts の置き換え・reviews の更新・log の追記・配信用の地図の作り直しを行う。
- 返り値は、保存した後の山頂の状態(GET と同じ形)。画面はこれを見て「確定」と表示する。

## 5. 管理画面

`admin/src/routes/admin-console/summit-maps/+page.svelte` を新しく作る。今の「SOTA × POTA」「Summit Maps」のアップロード欄もここに移す。

### 一覧

- 地域(JA/KN など)・状態・山頂コード・山名で絞り込む。
- 状態ごとの件数を上に出す(未確認・要確認・要再確認・確定)。
- 列: 山頂コード・山名・候補の組の数・推定の要約・状態・確定した人と日時。

### 詳細

見た目と操作は、見直しの判定表(claude.ai の artifact、`rereview/index.html`)のカードを引き継ぐ。違いは、データが本番の DB にあること、Firebase で入った管理者だけが確定できること、履歴と要再確認の扱いがあること。


- **判定用の地図**: ゾーン(赤)・山頂(▲)・最高点(○)・市区町村境(破線)・公園の元の区域(色)・100 m の目盛り。
- **最終形の地図**: 選んでいる答えで、FLEonline に出る形をその場で描く(確定前でも、選ぶたびに変わる)。
- **外部の地図へのリンク**: MyACT・地理院地図(山頂の位置で開く)。
- **地図の描き方**: 下地の GeoJSON を SVG で描く。FLEonline の MapSheet と同じ見え方にする(公園ごとの斜線の色と向き・区域の番号・ゾーン・市区町村境・山頂)。タイルの地図は使わない(外部への依存を増やさず、利用者の端末と同じものを見るため)。
  - 描き方(`PARK_STYLES` など)は、FLEonline の `summitMap.ts` と揃える。共通の部品にするかは、実装のときに決める(別の repo なので、最初は写して、出どころをコメントに書く)。
- **組の表**: 市区町村 × 公園ごとに 1 行。推定の答えと根拠(pct・px・note)を並べ、目視の答えは「全部 / 一部 / なし」のラジオボタン(**初期値なし**)。前に確定した答えがある場合は、それを初期値にしてよい(目視の答えなので)。ただし「要再確認」の山頂では、増えた組は初期値なしにする。
- **確定ボタン**: すべての組を選ぶまで押せない。押すと「保存中」になり、サーバーの返事で「確定(日時・誰が)」に変わる。失敗したら元に戻して、理由を出す。
- **状態の行**: 「あと N 組を選んでください」「選びました(まだ確定していません)」「保存しています…」「確定 日時・誰が」「保存できませんでした」を出し分ける(判定表と同じ)。
- **編集できるのは答えだけ。** ゾーン・公園区域・市区町村境の形は、管理画面では直さない。形が間違っているときは、目視の答えで正しい答えを入れ、元のデータ(公園区域の版・city_j の CSV など)を別に直す。答えの横に、直した理由のメモを書ける欄を置く(`summit_reviews.note`)。
- **目視の取り消し**ボタンと、**履歴**の表示。
- 「前の山頂」「次の山頂」ボタン(一覧の絞り込みの順)。確定しても自動では進まない。

本番の `summit_pota` の verified=1 は、all / part の組しか持っていない(98 行)。目視で「なし」と決めた組が DB にないので、手元の正本から作り直して入れる。

- 移行のための取り込み口(`POST /sota/review/import`、JSON)を一時的に作るか、マイグレーションの SQL に入れるかは、実装のときに決める。データを repo に置かないなら前者。
- 移したあと、山頂ごとの目視の組の数が、手元の正本と一致することを確かめる。

## 8. 進め方

デプロイは、まとめて 1 回にする。

1. マイグレーション(表 4 つの追加と、`summit_pota` から estimates への移し替え)。repository とそのテスト。
2. サービス: 答えの合成・状態の計算・地図の差し込み。PUT の検証(組の一致・409)。テスト。
3. API のハンドラーと OpenAPI。テスト。
4. 管理画面: 一覧・詳細・地図の SVG・確定の流れ。
5. バッチの変更(`input_rev`・差分の要約・山頂を絞った実行)と、移行用のデータ作り。
6. 手元(`$S/localrun/run.sh`)で通しで確かめる: 推定の取り込み → 目視の移行 → 管理画面で 1 山頂を確定 → 推定の取り込みをもう一度 → 目視が残り、組が変わった山頂だけが「要再確認」になる。
7. PR → 利用者がマージを指示 → デプロイ → 本番で、推定・下地・目視の移行を取り込む。
8. 本番の API で確かめる: YN-051(富士河口湖町 JP-0016 全部・目視)、GM-018(南魚沼市 JP-1354 全部・目視)、AC-006(東栄町 JP-0125 なし)、KN-029(JP-0118 と JP-1289)。地図の muni の `pota` も同じ答えになっていること。

## 9. テスト

- 取り込みで目視の行が変わらない。候補が減っても目視の行は残り、山頂は「要再確認」になる。
- 答えの合成: 目視が推定より優先され、目視の「なし」はその組を配信から外す。
- PUT: 組が足りない・余計な組がある → 400。`input_rev` が違う → 409。成功すると、log に変更が積まれ、配信用の地図の `pota` も変わる。
- 地図の差し込み: 「一部」でなくなった公園の park フィーチャが外れ、「一部」になった公園の park フィーチャが出る。
- 状態の計算(未確認・確定・要再確認・要確認・地図なし・推定が古い)。
- 山頂を絞った取り込みで、ファイルにない山頂の推定・地図・目視が変わらない。`mode=full` でも目視は消えない。
- 無効になった山頂・公園の組を配信しない。地図の差し込みでも外れる。
- 管理画面: 初期値が選ばれていない、全組を選ぶまで確定できない、保存に失敗したら戻る。

## 10. 参照データの増減

山頂の一覧は、SOTA の summitslist から定期的に自動で更新される(`update_summit_list_from_file`。有効期間外の山頂は消える)。公園の一覧は、管理者が CSV で取り込む(`park_inactive` がある)。公園区域・市区町村境・JCC/JCG の表は、手元のバッチの材料。どれが変わっても、目視を黙って使い続けない・見ていない答えを目視扱いにしない、を守る。

### 10.1 入力の指紋(`input_rev`)

バッチが、山頂ごとに「その山頂の推定を決めた入力」の指紋を計算して、推定と一緒に入れる。

- 中身: 山頂の位置(小数 5 桁)、ゾーンの形、ゾーンにかかる市区町村のキー(JCC/JCG)とその区域の形、候補の公園のコードとその区域の形。
- 入力が変わっていない山頂は、データの版を上げても指紋が変わらない。そのため、版を上げるたびに全山頂が要再確認になることはない。変わった山頂だけが要再確認になる。
- 目視は、確定したときの `input_rev` を持つ。今の推定の `input_rev` と違えば要再確認。

### 10.2 場合ごとの扱い

| 変化 | 気づき方 | 配信 | 目視 |
|---|---|---|---|
| 山頂が増えた | `sota_references` にあって推定・地図がない(状態「地図なし」) | 何も返さない(今と同じ) | バッチを流すと「未確認」になる |
| 山頂が無効になった・消えた | 定期更新で `sota_references` から消える | `sota_references` にない山頂は返さない(JOIN で落とす。地域の地図にも入れない) | 消さずに残す(履歴)。同じコードで戻ってきたら、10.1 で判断 |
| 山頂の位置が変わった | `sota_references` の位置と、`summit_estimates_meta` の位置が 20 m 以上ずれる(状態「推定が古い」) | 古い推定のまま返す | バッチを流すと `input_rev` が変わり、要再確認 |
| 公園が増えた | 公園区域の新しい版で、バッチを流す | — | 候補の組が増えた山頂だけ要再確認 |
| 公園が無効になった・消えた | `pota_references` で `park_inactive`、または行がない | その公園の組は返さない(JOIN で落とす。地図の差し込みでも外す) | 残す。次のバッチで候補から消えれば要再確認 |
| 公園区域が変わった(v25 など) | 新しい版でバッチを流す | — | 区域が変わった公園にかかる山頂だけ要再確認 |
| 市区町村の合併・JCC/JCG の変更 | munitable・N03 の新しい版でバッチを流す | — | キーが変わった山頂は要再確認。前のキーの目視は「前の目視(旧○○町: 全部)」として参考に出す |
| 公園名・山名の変更 | 参照の表の更新 | 名前は配信のときに参照の表から引く(地図にも差し込む) | 影響なし |

### 10.3 要再確認の山頂の画面

- 前の目視の答えは**参考の列**に出し、ラジオボタンの初期値にはしない(前提が変わったので、今の地図で見直してもらう)。
- 何が変わったか(位置・公園区域・市区町村のキー・増えた組・消えた組)を、推定の差分として出す。そのため、バッチは前の入力との差分の要約(`note`)を山頂ごとに付ける。
- 確定するまでは、配信は前の目視のまま。消えた組の目視は配信しない(候補にない組は返さない)。増えた組は推定で返す。

### 10.4 バッチの流し方

- 推定と地図の取り込みは、**ファイルに入っている山頂だけ**を置き換えるようにする(今の推定の取り込みは全件を置き換えている)。これで、増えた山頂・位置が変わった山頂だけを流して取り込める。
- 全件を流し直したときに、ファイルにない山頂を消すかどうかは、取り込みの引数で明示する(`mode=full` のときだけ、ファイルにない山頂の推定・地図を消す。目視は消さない)。
- 管理画面に「推定が要る山頂」(地図なし・推定が古い)の一覧と CSV の書き出しを置き、バッチはそれを入力に取れるようにする。
- 定期更新で山頂が増えても、自動ではバッチを流さない(空間計算は手元で行う方針のため)。管理画面の件数で気づく。
