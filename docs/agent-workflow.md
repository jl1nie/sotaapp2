# エージェントの進め方: どのモデルでループを回し、いつ任せるか

状態: このリポジトリでの Claude Code の標準(2026-10-25 から)。sotalive-monorepo・mfsk-core と同じ考え方で、表の中身だけをこのリポジトリに合わせている。
根拠: Anthropic「Building agents: when to fold subagents into your main agent loop」
(<https://claude.com/ja/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop>)。

## 1. 前の決まりが高くついた理由

記事の結論は、**1 つのループで、文脈を必要なときに読み込む**方が、サブエージェントに分けるより、品質・費用・速さのどれもよいことが多い、というもの。任せるたびにモデルのループが入れ子になり、戻ってくる要約は細部を落とす。すべての手順を見たエージェントは手順どうしをつなげられるが、要約の束にはそれができない。

前の決まり(「設計は Opus・実装はいつも Sonnet のサブエージェント」。メモリにだけあった)は、1 つの変更で同じファイルを 3 回読んでいた。

1. Opus の主のセッションが、仕様を書くためにコードを読む。
2. Sonnet のサブエージェントが、実装するために同じファイルを読み直す。
3. Opus が差分と報告を読み直す。そのあいだ、主のループはずっと Opus。

小さな変更では、1 と 3 だけで、Sonnet が 1 つのループで全部やるより高い。**費用を決めるのは、主のループを回すモデル**で、エージェントの数ではない。

## 2. 主のループのモデルを、作業の種類で選ぶ

既定は `opusplan`(`.claude/settings.json`)。plan mode では Opus、計画を承認して実行に移ると、同じループ・同じ文脈のまま Sonnet になる。仕様を渡し直さず、読み直さない。

| 作業 | 主のループ | 理由 |
|---|---|---|
| 承認した設計の実装、管理画面(`admin/`)、今の書き方に沿ったハンドラー・repository、CSV の取り込みの手直し、`.sqlx` の作り直し、docs、CI、デプロイの手順 | **Sonnet** | 判断は済んでいて、読み書きの量の仕事 |
| 設計: DB のスキーマとマイグレーション、認証と権限、FLEonline・MyACT が使う API の形、アワードの判定、山頂の POTA の判定(`docs/summit-map-admin-*.md`) | **Opus**(plan mode) | 設計を間違えるのがいちばん高くつく |
| 原因の調べ: 本番の不具合で、原因がまだ分からないもの(APRS の受信ループの空回りなど) | **Opus** | 仮説を並べて絞るのが難しいところ |
| 状態の質問、「X はどこ」 | **Sonnet**(または `Explore`) | 調べもの |

作業の種類が変わったら、`/model` でセッションの中で切り替える(文脈は残る)。機械的な作業は effort を下げる。

## 2a. 計画に種類を書く

計画は、先頭に 2 行を書く: `Type: feature | fix | data | docs | infra` と、`本番: …`(本番への影響。なければ「なし」。`Type: docs` では省ける)。本番は Fly.io の小さな 1 台(shared-cpu-1x、メモリ 256 MB)で、FLEonline・MyACT・sotalive-monorepo の Pages Functions が同じ API を使う。Deploy は手動のワークフロー(`gh workflow run deploy.yml`)なので、**Deploy の有無とバックアップ**も、ここで言う。種類は、計画のループが自分で言う(常駐のエージェントは置かない)。

| 種類 | 計画に書く証拠 | 例 |
|---|---|---|
| feature | 新しい公開の入口(API・クエリのパラメーター・ヘッダー・マイグレーション・役割)ごとに、**定義**(何を意味するか)、**誰が設定するか**、**間違っていたら落ちるテスト**(一度は落ちるのを見る) | `Cache-Control`(`cached` ミドルウェア): 公開の読み取り API ごとに、max-age の値。ヘッダーが付かなければ落ちるテスト。地図の本体(`/sota/maps`)は、版の問い合わせだけが新しくなるのを避けるため、付けない |
| fix | **直す前に落ちるテスト**(または再現の手順)と、直したあとの確認 | `/pota` の遅さ: 実行計画のテスト(`EXPLAIN QUERY PLAN` に全行の走査・一時的な索引がない)が、直す前は落ちる |
| data | DB・件数・本番への取り込み。**バックアップ**、標本での検証(`--sample 300 --workers 2`。全件を本番に投げない) | 推定・地図・目視の取り込み。`Deploy` ワークフローの `Backup Database` に頼らず、取り込みの前に写しを取る |
| docs / infra | なし(`本番:` の行だけ) | docs、CI、スクリプト、hook |

`.claude/hooks/plan-mode-guard.sh` が、`Type:` のない計画、feature に「落ちる」がない計画、fix に「落ちる」か「再現」がない計画、data に「バックアップ」がない計画、`本番:` のない計画(docs 以外)を、`ExitPlanMode` で拒む。誤って拒まれて進めなくなったときは、環境変数 `PLAN_GUARD=off` で止められる(使ったら、計画に理由を書く)。記録は `docs/agent-log.md`(7 章)。

## 3. サブエージェントを使うとき

記事の 3 つの条件のどれかに当たるときだけ使う。

| 条件(記事) | このリポジトリでは | エージェント |
|---|---|---|
| **文脈がふくらむ**と主のループが鈍る | `cargo make test` / `clippy` の全部のログ、`docker build`、`fly logs`、`cargo sqlx prepare`。数千行のうち、要るのは数値と失敗だけ | `runner`(Sonnet)。数値と失敗だけを返す |
| **互いに関係のない並列の作業**で、文脈を捨ててよい | Rust 側と管理画面(`admin/`)を同時に作る。触るファイルが重ならないもの | 1 つのメッセージで `runner` をいくつか |
| **書いた人の結論に引きずられない読み**が要る | テストでは判断できない変更(4 章) | `reviewer`(Opus)。差分と仕様を渡し、書いた人の結論は渡さない |

次のときは**使わない**:

- 主のループで数か所を編集すれば済む(指示を書く方が高い)。
- 次の手順が、要約が落とす細部に左右される(原因の調べ、設計)。
- 探す先がもう分かっている調べもの。
- 実装を別のモデルでしたい: `/model` で切り替える。**`fork` で実装しない**(主のモデルを引き継ぐ)。

## 4. レビュー: `reviewer` が要るとき

決め手は、**テストがその変更を判断できるか**。迷ったら「これが間違っていたら、どのテストが落ちるか」と問う。名前を挙げられて、それを走らせたなら、レビューは要らない。

**要らない**(テストと pre-commit の fmt・clippy・test がレビューの代わり):

- 前に落ちて後で通るテストのあるバグの直し。
- 今の書き方に沿った、テストのあるハンドラー・repository・service の追加。
- 管理画面の見た目、docs、CI、テストだけの変更。

**要る**(テストでは判断できない):

- 本番のデータに効く、元に戻せないマイグレーション(表や列を消す・移す、既定値を変える)。テストは空の DB にかけるので、本番の今のデータで移れるかは判断できない。
- 認証と権限(`with_auth`、ミドルウェア、役割)。
- FLEonline・MyACT(sotalive-monorepo)が読む API の形。相手の側のテストはこのリポジトリでは走らない。
- アワードの判定の規則。

## 5. トークンの節約(どのモデルでも)

- 必要なときに読む: `CLAUDE.md` は目次。リンク先の文書は、作業に要るときに読む。
- 大きなファイル(`Cargo.lock`、`.sqlx/`、`static/`、取り込みのデータ)は読まないか、`grep -n` で場所を見てから、その範囲だけを読む。
- 長いコマンドは `tail -n 40` か `grep -E 'FAILED|error|panicked|test result'` で絞る。直しているあいだは 1 つのテスト(`cargo nextest run <名前>`)か 1 つのパッケージだけを回し、全体は仕上げに 1 回。
- 互いに関係のないツールの呼び出しは、1 回のターンにまとめる。
- 新しい進め方を試したときは、作業の終わりに `/cost` を見る。比べるのは同じ種類の作業どうし(7 章)。

## 6. ハーネスが守らせるもの、助言のもの

`CLAUDE.md` はモデルが読む文脈で、関門ではない。文脈が長いときや急ぐ作業では飛ばされることがある。大事な決まりは、ハーネスが実行する層に移す。

| 決まり | 層 | 守らせるか |
|---|---|---|
| 主のモデルの既定は `opusplan` | `.claude/settings.json` の `model` | セッションの始めに効く。明示して選んだモデル(`/model`、`--model`、アプリのモデルの選択)はこれより優先される |
| `runner` は Sonnet、`reviewer` は Opus | `.claude/agents/*.md` の `model:` | 効く |
| `fork` を使わない、`runner` に `model` を指定しない | `Agent` の PreToolUse の hook: `.claude/hooks/agent-guard.sh`(呼び出しを拒む) | 効く |
| fmt・clippy・test | `.git/hooks/pre-commit`(Rust のファイルをコミットするとき)と CI | 効く |
| 「通ったか」: 最後の 1 行、正直な終了コード、コミットしたものをきれいなチェックアウトで試す(admin の build を含む) | `scripts/verify.sh`(`--quick` で clean を飛ばす) | 走らせたときだけ。作者が最後の 1 行を読む(8.1) |
| 「CI が通ったか」、**Deploy の前のイメージ** | `scripts/ci-wait.sh [sha] [--need REGEX]`(`--need 'Docker Build'`) | 走らせたときだけ(8.1) |
| 計画に `Type:`・`本番:` と、その種類の証拠を書く | `ExitPlanMode` の PreToolUse の hook: `.claude/hooks/plan-mode-guard.sh`(呼び出しを拒む) | 効く |
| いつ任せるか(3 章)、いつモデルを替えるか(2 章)、レビューが要るか(4 章) | この文書 | 助言。hook にはできない判断 |

`CLAUDE.md` に決まりを足す前に、それが機械的なもの(パス・フラグ・ツールの引数)かを問う。機械的なら hook かスクリプトに入れ、`CLAUDE.md` はそこを指すだけにする。

## 7. この標準を変えるとき、記録

コードと同じく測る。代表的な作業をいくつか選び(docs の直し、テストのあるバグの直し、管理画面の直し、レビューの要るマイグレーション)、結果(最初のゲートで通ったか、レビューが本当の欠陥を見つけたか)を記録する。1 つだけ変えて比べる。結論の前に、同じ作業を 2 回以上走らせる。記事の例の後退は、2 回のうち 1 回にしか出なかった。

記録は `docs/agent-log.md`。作業が終わったら(`scripts/ci-wait.sh` が `CI PASS` と言ったあとに。Deploy まで含む作業は、Deploy の確認のあとに)`scripts/agent-log.sh <作業> <種類> --base <作業の最初のコミットの前の rev> ...` で 1 行を足す。トークンはセッションの記録とサブエージェントから測る。最初のゲートで通ったか・レビューの結果・push 後の修正・利用者の訂正は、フラグで渡し、渡さなければ `?`(推測しない)。**セッションの全体を数える**ので、1 つのセッションで複数の作業をしたときは、あとの行にそれまでの全部が入る。1 セッション 1 作業で記録するか、行の差を読む。2 つのリポジトリ(sotaapp2 と sotalive-monorepo)にまたがる作業は、セッションを始めたリポジトリの記録に書き、もう一方の PR はメモに書く。

**月の最初の作業日(または記録が 10 行たまったとき)に**、`scripts/agent-log.sh --summary <前回の日付>` を見て、プロセスの変更を**最大 1 つ**提案し、次の月に比べる。リリースの周期がないリポジトリなので、月で区切る。

## 8. 検証の規律

2026-10-25 の作業で起きたことは、設計の誤りよりも、確認を**走らせて読み違えた・違うものに走らせた・走らせなかった**ことだった。下の規則は、それぞれ、仕組みを名指しする。

**8.1 結果は 1 行。** `scripts/verify.sh` を直接走らせる(`run_in_background` で、まわりに何も足さない。`cmd > log; echo $?` にしない)。**最後の行**が `VERIFY PASS` か `VERIFY FAIL: <段階>` で、終了コードもそのとおり。ラッパーの終了コードはラッパーのもので、スクリプトの失敗を隠す。push のあとは、`scripts/ci-wait.sh [sha] --need 'Docker Build'` が、CI について同じことをする(`--need` は、変更に効くジョブを名指しする。ないジョブは失敗)。**PR は、CI が終わってからマージする**(`gh pr merge` は、CI の実行中でも通る。#48 は、Lint と Test の実行中にマージした)。

**Deploy の前に、`main` のイメージがあることを見る。** マージのあと、`scripts/ci-wait.sh <main の sha> --need 'Docker Build'` が `CI PASS` と言ってから、`gh workflow run deploy.yml`(バックアップは省かない)。続けて、`Backup Database`・`Resolve Image`・`Deploy to Fly.io` の成功と、API の応答(例: `/api/v2/sota/maps/versions?prefix=JA%2FST` が 200)を見る。2026-10-25 に、マージ直後に Deploy を走らせて、`Resolve Image` で「Image not found」になった(本番には何も出なかった)。なお、`docs/**` と `**.md` だけの push は CI が走らない(`paths-ignore`)ので、`ci-wait.sh` は「実行が出てこない」と言う。docs だけなら、それで正しい。

**8.2 この手元で通ったことは、通ったことではない。** `.env.test` などの `.env.*` は git に入れない。手元にだけあるファイルに頼って通っても、CI では通らない。管理画面の `npm run build` は、追跡している `static/` を書き換える(手元で走らせると作業ツリーが汚れる)。`verify.sh` の `clean` の段階が、コミットした HEAD を、きれいなチェックアウトで、CI と同じ環境(`SQLX_OFFLINE=true`、`.env.test` なし)で試し、admin の build もここで試す。**先にコミットする**(HEAD を試す)。もう 1 つ: 手元の速さは、本番の速さではない。`/pota` の遅さは、手元とステージングの速い CPU では目立たず、本番(shared-cpu-1x)で 3〜13 秒になった。クエリは `EXPLAIN QUERY PLAN` で全行の走査がないことをテストする。

**8.3 サブエージェントの報告は、手がかりで、事実ではない。** 調査の報告の数値や挙動を、docs・Issue・返信に書く前に、それを示す 1 つのコマンドを、自分で走らせ直す。JA/ST-004 の「POTA なし」は、端末の古い保存データを疑ったが、サーバーのデータは正しく(`/sota/summits/{code}/pota`、移行前の出力の `summit_pota.csv`)、実際は管理画面のプレビューが、未選択の組を「なし」として描いていた。原因を言う前に、データの出どころを見る。

**8.4 docs の主張には、テストか測定がある。新しい公開の入口には、計画に 3 行ある。** 3 行は、定義(呼び出しごとか、期間ごとか)、誰が設定するか、定義が間違っていたら落ちる 1 つのテスト。管理画面の「配信される地図」は、未選択の組の扱いを決めていなかった(`buildServedMap` が、選んだ答えだけから作っていた)。「未選択は推定で描く」というテストがあれば、画面を見る前に気づけた。

**8.5 一括編集のあとは、ビルドとテストを走らせ、差分を読む。** `sed`・Python の置換は、狙った所以外にも当たる。置換のあとは `git diff` を読み、`verify.sh --quick` を走らせる。

**8.6 待つことは、止まる理由ではない。** `verify.sh` や `ci-wait.sh` をバックグラウンドで始め、それに左右されない仕事を先に進める。その仕事は、push の前に挙げる(あとではなく)。止まるのは、利用者の判断が要るときだけ(本番の設定変更・Deploy・取り込みは、利用者の指示を待つ)。

**8.7 reviewer への依頼。** 意図を 2 文で書く。見てほしい点を並べる(マイグレーションが本番の今のデータで移れるか、権限の抜け、API の形が FLEonline・MyACT の読み方を壊さないか)。**検証のログのパスを渡し、ゲートを走らせ直さないように言う**(結果を疑う 1 つのコマンドだけ、走らせ直してよい)。確かめていないこと(本番のデータでの動き、実機の見た目)を言う。`.claude/agents/reviewer.md` に、いつも書くことがある。
